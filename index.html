Открываем консоль купленного сервера

Облачный сервер Timeweb уже куплен. Начинаем урок с входа в его веб-консоль Ubuntu — прямо в браузере, без SSH с ноутбука.

  1. Откройте Timeweb Cloud → Облачные серверы → свой VPS.
  2. Перейдите в раздел «Консоль» (веб-консоль сервера).
  3. Войдите как root с паролем из панели, если вход не выполнен автоматически.
  4. Убедитесь, что приглашение похоже на root@имя-сервера:~#.
Проверяем версию UbuntuTIMEWEB · ROOT
cat /etc/os-release | head -n 5
i
Что уже подготовлено

У нас есть оплаченный VPS с Ubuntu 24.04, готовый Telegram-бот в Cursor, существующий GitHub-репозиторий и GitHub Desktop. Покупать сервер и создавать репозиторий заново не нужно.

✓
Почему веб-консоль?

Все команды мы вводим прямо в консоли Timeweb. Это работает даже тогда, когда подключение SSH из Cursor или ноутбука не получается из-за VPN.

ШАГ 05 / 14 · ПЕРВЫЙ ДЕПЛОЙTIMEWEB · ROOT

Вводим токены безопасно

BOT_TOKEN и OPENAI_API_KEY задаются непосредственно на VPS, не в GitHub Actions и не в публичном репозитории.

!
Приостановите запись экрана

Вставка токенов через буфер обмена и показ приватного SSH-ключа не должны попасть в обучающее видео. Никому не отправляйте ключи и пароли.

Введите токен Telegram — символы скрытыTIMEWEB · ROOT
read -rsp "BOT_TOKEN: " BOT_TOKEN; echo
Введите OpenAI API key — символы скрытыTIMEWEB · ROOT
read -rsp "OPENAI_API_KEY: " OPENAI_API_KEY; echo
Сохраните файл .envTIMEWEB · ROOT
cd /opt/tg-bot-podarok
umask 077
printf 'BOT_TOKEN=%s\nOPENAI_API_KEY=%s\n' "$BOT_TOKEN" "$OPENAI_API_KEY" > .env
unset BOT_TOKEN OPENAI_API_KEY
chown deploybot:deploybot .env
chmod 600 .env
test -s .env && echo "Настройки сохранены"
i
Что делает этот шаг

Файл .env появится только на сервере. Он исключён из Git. После редеплоя Docker Compose использует те же настройки.

Готовим сохранение данных

Папка data хранит счётчик открыток и должна переживать пересборку контейнера.

Проверить настройку volumeTIMEWEB · ROOT

Зачем это нужно

Готовим SSH-ключ для GitHub Actions

Теперь GitHub сможет безопасно подключаться к серверу без ввода пароля.

Создать SSH-ключ на сервереTIMEWEB · ROOT
install -d -m 700 /root/.ssh
ssh-keygen -q -t ed25519 -N "" -f /root/.ssh/gh_actions_deploy -C "github-actions-timeweb"
Разрешить вход ключом пользователю deploybotTIMEWEB · ROOT
install -d -m 700 -o deploybot -g deploybot /home/deploybot/.ssh
cat /root/.ssh/gh_actions_deploy.pub >> /home/deploybot/.ssh/authorized_keys
chown deploybot:deploybot /home/deploybot/.ssh/authorized_keys
chmod 600 /home/deploybot/.ssh/authorized_keys
!
Приватный ключ — только в GitHub Secrets

Следующую команду выполняйте с ПРИОСТАНОВЛЕННОЙ записью экрана. Никому не отправляйте приватный ключ. Начало ключа — BEGIN OPENSSH PRIVATE KEY; скопировать нужно весь многострочный текст.

Показать приватный ключ для сохранения в GitHub SecretTIMEWEB · ROOT
cat /root/.ssh/gh_actions_deploy
i
Что будет дальше

Скопируйте результат в GitHub Secret VPS_SSH_PRIVATE_KEY, а после настройки удалите временные файлы ключа с сервера — это отдельный шаг ниже.

ШАГ 09 / 14 · АВТОДЕПЛОЙTIMEWEB · ROOT

Получаем SSH host key сервера

GitHub Actions должен проверять, что подключается именно к нашему VPS.

Показать host key в формате known_hostsTIMEWEB · ROOT
printf '__IP__ '; awk '{print $1, $2}' /etc/ssh/ssh_host_ed25519_key.pub
i
Скопируйте всю строку

Она начинается с вашего внешнего IP, затем ssh-ed25519 и длинная строка. Это значение для GitHub Secret VPS_KNOWN_HOSTS. Если вы переустановите ОС, host key изменится — секрет потребуется обновить.

Проверить SSH-серверTIMEWEB · ROOT
systemctl is-active ssh && ss -lnt | grep ":22"
!
Доступность порта 22

В панели Timeweb проверьте сетевой экран: TCP 22 должен быть доступен для SSH-соединения GitHub Actions. Не отключайте проверку host key и не публикуйте приватный ключ.

ШАГ 10 / 14 · АВТОДЕПЛОЙGITHUB · БРАУЗЕР

Добавляем 3 секрета в GitHub

Секреты нужны только для SSH-доступа GitHub Actions к VPS. BOT_TOKEN и OPENAI_API_KEY остаются в .env на сервере.

  1. Откройте СУЩЕСТВУЮЩИЙ GitHub-репозиторий бота.
  2. Нажмите Settings → Secrets and variables → Actions → Secrets.
  3. Нажмите New repository secret три раза и заполните значения из таблицы.
  4. Убедитесь, что названия написаны точно, заглавными латинскими буквами.
ИМЯ СЕКРЕТАЗНАЧЕНИЕ
VPS_HOSTВнешний IPv4 сервера Timeweb; например, поле IP вверху гайда.
VPS_SSH_PRIVATE_KEYВесь многострочный закрытый ключ из cat /root/.ssh/gh_actions_deploy.
VPS_KNOWN_HOSTSСтрока из предыдущего шага: IP ssh-ed25519 AAAA...
!
Не добавляйте секреты в код

Секреты сохраняются только в Settings → Actions secrets. Не включайте запись экрана при показе содержимого приватного SSH-ключа.

Удаляем временный приватный ключ

После сохранения ключа в GitHub Secrets удалим его временную копию из папки root на VPS.

!
Перед удалением

Убедитесь, что GitHub Secret VPS_SSH_PRIVATE_KEY действительно сохранён полностью: секрет потом нельзя просто прочитать обратно.

Удаляем временную пару ключейTIMEWEB · ROOT
rm -f /root/.ssh/gh_actions_deploy /root/.ssh/gh_actions_deploy.pub

Да, новый SSH-ключ можно создать и добавить в authorized_keys, если потребуется его заменить. Удаление временного файла не затрагивает уже запущенного бота.

ШАГ 12 / 14 · АВТОДЕПЛОЙCURSOR

Создаём файл GitHub Actions

В нашем существующем проекте создаём файл .github/workflows/deploy.yml. Никаких новых репозиториев.

  1. Откройте проект бота в Cursor.
  2. В корне создайте папку .github, внутри — workflows, внутри — deploy.yml (если их ещё нет).
  3. Откройте файл deploy.yml и вставьте содержимое ниже. Также готовый файл есть в ZIP рядом с гайдом.
  4. Обратите внимание: ключи и пароли внутри YAML НЕ пишутся. Он берёт их из GitHub Secrets.
Полный файл .github/workflows/deploy.ymlCURSOR · ФАЙЛ
name: Deploy Telegram bot to Timeweb

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: telegram-bot-deploy
  cancel-in-progress: false

jobs:
  deploy:
    name: Update bot on VPS
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - name: Configure SSH safely
        shell: bash
        env:
          VPS_SSH_PRIVATE_KEY: ${{ secrets.VPS_SSH_PRIVATE_KEY }}
          VPS_KNOWN_HOSTS: ${{ secrets.VPS_KNOWN_HOSTS }}
        run: |
          set -euo pipefail
          test -n "$VPS_SSH_PRIVATE_KEY"
          test -n "$VPS_KNOWN_HOSTS"
          mkdir -p "$HOME/.ssh"
          chmod 700 "$HOME/.ssh"
          printf '%s\n' "$VPS_SSH_PRIVATE_KEY" > "$HOME/.ssh/id_ed25519"
          printf '%s\n' "$VPS_KNOWN_HOSTS" > "$HOME/.ssh/known_hosts"
          chmod 600 "$HOME/.ssh/id_ed25519" "$HOME/.ssh/known_hosts"

      - name: Pull and deploy on Timeweb
        shell: bash
        env:
          VPS_HOST: ${{ secrets.VPS_HOST }}
        run: |
          set -euo pipefail
          test -n "$VPS_HOST"
          ssh -i "$HOME/.ssh/id_ed25519" \
              -o StrictHostKeyChecking=yes \
              -o BatchMode=yes \
              -o ConnectTimeout=20 \
              deploybot@"$VPS_HOST" 'sh -se' <<'REMOTE'
          cd /opt/tg-bot-podarok
          git fetch origin main
          git merge --ff-only origin/main
          docker compose up -d --build
          docker compose ps
          for attempt in 1 2 3 4 5 6; do
            if curl --fail --silent http://127.0.0.1:8080/health >/dev/null; then
              echo "Bot health check: OK"
              exit 0
            fi
            sleep 5
          done
          docker compose logs --tail=60 bot
          echo "ERROR: bot health check did not pass" >&2
          exit 1
          REMOTE
i
Что делает автоматизация

При Push в ветку main GitHub Actions подключается по SSH к пользователю deploybot, делает git fetch + merge --ff-only, выполняет docker compose up -d --build и проверяет /health.

ШАГ 14 / 14 · ФИНАЛTIMEWEB / GITHUB

Проверка и частые ошибки

Бот отвечает без Cursor, а новый код попадает на VPS автоматически после Commit + Push.

Нужно каждый день запускать Docker?

Нет. В docker-compose.yml указан restart: unless-stopped. Бот продолжает работать на VPS после выключения ноутбука; автоматизация нужна лишь для обновлений.

Commit + Push есть, а бот старый. Почему?

Зайдите на GitHub → Actions. Если запуск красный — откройте лог ошибки. Если зелёный — убедитесь, что в main лежит новая версия, а локальная копия бота остановлена.

В GitHub Actions Permission denied (publickey)

Не совпал SSH-ключ, не добавлен публичный ключ в /home/deploybot/.ssh/authorized_keys, неверный VPS_HOST или пользователь.

Connection timed out / Connection refused

Проверьте внешнюю доступность TCP-порта 22 и службу ssh на VPS. Консоль Timeweb при этом может продолжать работать.

Host key verification failed

GitHub Secret VPS_KNOWN_HOSTS не совпадает с текущим SSH host key сервера. При переустановке Ubuntu он меняется.

Docker permission denied

Проверьте id deploybot: пользователь должен входить в группу docker. Для его SSH-сессии должно примениться новое членство.

Бот не создаёт открытки

Проверьте бот-логи, корректность OPENAI_API_KEY, доступность нужной модели и права папки data.

Ошибка Telegram Conflict

Одновременно работают два polling-процесса с одним токеном. Остановите локальную копию python run.py или другой серверный экземпляр.

Куда исчез .env после Push?

Он никуда не должен исчезать: .env находится только на VPS. GitHub его не обновляет, git merge сохраняет игнорируемый файл.

Проверить контейнер и логи вручную, только если нужноTIMEWEB · ROOT
cd /opt/tg-bot-podarok && docker compose ps && docker compose logs --tail=40 bot
Перезапустить контейнер без обновления кода, только если нужноTIMEWEB · ROOT
cd /opt/tg-bot-podarok && docker compose restart
